# GPU 可行性（2026-11-21，已实测）

> 目的：不是"把训练搬到 GPU"，而是量清楚**什么规模才轮得到 GPU**。
> 工具：`gpu_probe.py`。下面是 RTX 5070 上的实测结果。

## 0. 结论先说

1. **对这个项目：GPU 更慢，不要迁。**
   H=30 / batch=8000（就是项目现在的模型）训练一步：CPU 0.60 ms，GPU 1.07 ms，**0.6×**。
   推理（batch=10，游戏里每次决策）：CPU 0.032 ms，GPU 0.048 ms，**0.7×**。
2. **GPU 有一个约 1 ms/步的固定开销，CPU 约 0.5 ms。**
   证据：batch=2048 时，H 从 30 涨到 6400（算力差 200 倍），GPU 耗时只从 1.06 变 1.14 ms。
   所以小模型上 GPU 全是开销。
3. **GPU 真正开始赢的门槛：H ≥ 1600 且 batch ≥ 2048。**
   那里加速比 3×；H=6400 / batch=8000 也只有 **15×**（不是几十倍——仍然没跑满算力）。
4. 项目里**最贵的那部分 GPU 碰不到**：一次重训 ≈ 48 分钟搜索采样 + 2 分钟训练，
   训练只占 4%；而采样是纯 Python rollout（单次 87 µs，Lv3 一个决策 6.2 ms），
   不可向量化。

## 2. 实测：训练一步（ms，68 → H → 1，MSE + Adam）

| H | batch | CPU | GPU | 加速比 |
|---|---|---|---|---|
| 30 | 256 | 0.65 | 0.50 | 1.3× |
| 30 | 2048 | 0.47 | 1.06 | **0.4×** |
| 30 | 8000 | 0.60 | 1.07 | **0.6×** |
| 120 | 2048 | 0.57 | 0.91 | 0.6× |
| 120 | 8000 | 0.92 | 1.04 | 0.9× |
| 400 | 2048 | 1.04 | 0.91 | 1.1× |
| 400 | 8000 | 2.46 | 0.97 | 2.5× |
| 1600 | 2048 | 2.84 | 0.96 | 3.0× |
| 1600 | 8000 | 14.5 | 1.09 | **13.3×** |
| 6400 | 2048 | 15.1 | 1.14 | 13.3× |
| 6400 | 8000 | 67.6 | 4.41 | **15.3×** |

**读法**：GPU 那一列几乎是常数（≈1.0 ms）直到 H=6400/batch=8000 才动，说明
瓶颈是**每步固定开销**（~30 个 kernel 启动 + Python 调度），不是算力。
这也是为什么加速比封顶在 15×，而不是显卡的理论倍率。

## 3. 实测：推理一次（ms）

游戏里每次决策的 batch 是 ≤10；离线批量打分才会到 1024+。

| H | batch 10 | 1024 | 16384 |
|---|---|---|---|
| 30 | CPU 0.032 / GPU 0.048（**0.7×**） | 0.074 / 0.050（1.5×） | 0.177 / 0.117（1.5×） |
| 400 | 0.042 / 0.116（**0.4×**） | 0.141 / 0.121（1.2×） | 1.85 / 0.169（10.9×） |
| 6400 | 0.077 / 0.117（**0.7×**） | 1.74 / 0.163（10.7×） | 60.4 / 3.69（16.4×） |

**结论**：对局时的推理**永远不该走 GPU**——batch=10 时 GPU 全是启动开销，
而且一次决策要算 10 次，GPU 版本每次都要多付一次 kernel 启动。

## 4. 实测：搜索（纯 Python）

```
4 人局单次 rollout: 86.8 微秒（单线程）
Lv3 一个决策 = 前 3 名 × 24 次 = 72 次 rollout ≈ 6.2 毫秒
```

`simulateRestN` 是 Python 循环 + 随机 + 可变长度的行结构，**不可向量化**，
GPU 完全用不上。而它才是这个项目真正的开销。

## 5. 所以对"重训"的结论

**用 3.8 + CPU 训练，不要为了这次重训迁到 GPU。**

- 模型是 H=30~400，正好落在 GPU 最吃亏的区间；
- 就算 H 上到 1600，训练也只从 2 分钟缩到 10 秒，而数据采样那 48 分钟一点没变；
- 算笔更细的账：现在一个模型训 8004 步实测 **11.9 秒（1.49 ms/步）**，
  其中纯 torch 步进只有 0.60 ms，剩下 0.89 ms 是取数据/日志等循环开销。
  换到 GPU 后纯步进变 1.07 ms，总时间反而变成 ~1.96 ms/步 → **16 秒，更慢**。
- 迁到 3.13 还要验证 `neural_network_template` 的导入路径和整个评测链路。

**什么时候值得回来开 GPU**：

| 场景 | 值不值 |
|---|---|
| 模型 H ≥ 1600、batch ≥ 2048 | 值（3~15×） |
| 换成 Transformer / 大输入 | 值（算力才吃得满） |
| 离线批量打分（batch ≥ 1024） | 值（10~16×） |
| 对局时的单步推理（batch ≤ 10） | **永远不值** |
| 搜索 / 数据采样 | **永远不值**（纯 Python） |

## 6. 迁移成本（已验证可行，但不是免费的）

- torch 2.15(3.13) 能读 2.4(3.8) 存的整模型，反向也测通了 → **可以"GPU 训练 + CPU 对局"**；
- 但 `neural_network_template` 不在项目目录，要靠 `sys.path.append('../202308_Neural_Network')`；
- 3.13 下 `torch.load(weights_only=False)` 需要该模块可导入，否则模型加载会报 `ModuleNotFoundError`。

一句话：**路是通的，但对这个项目没有必要走。**

## 7. 一条能带走的判断

> 小模型的 GPU 加速比由**固定开销**决定，不由显卡决定。
> 本项目 H=30 时，GPU 的 1 ms 启动开销是计算本身的 2 倍以上。
> 决定要不要上 GPU，先量"每步固定开销 × 步数"占训练总时长的比例——
> 这个项目里它接近 100%，而更外层的数据采样又完全是另一个数量级。
